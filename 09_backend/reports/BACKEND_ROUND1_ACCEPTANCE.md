## 6 Architecture

The implementation is a domain-first FastAPI application orchestrator/BFF.
Routers parse requests and map DTOs; domain services own workflow ordering;
integration ports isolate upstream capabilities; memory adapters provide the
Round 1 persistence seam. Backend does not calculate CAT theta/SE, implement
retrieval/reranking or Safety policy, call Ollama, or create a database schema.

## 7 Application Factory / Lifespan

`create_app()` wires settings, routers, middleware, exception handlers, OpenAPI
metadata, and the modern FastAPI lifespan. Lifespan starts and closes
long-lived clients and configures logging. Importing `main` does not make
network calls. App factory, liveness, readiness, and dependency health tests
passed.

## 8 Authentication

Login, logout, `me`, and CSRF-token retrieval are implemented with synthetic
users. Invalid usernames and passwords use the same public error semantics.
Argon2 password verification is server-side and passwords/hashes are not
logged. Registration, password reset, OAuth/OIDC, and MFA are deferred.

## 9 Session

Authentication uses an opaque server-side session reference generated by
`secrets.token_urlsafe(32)`. Login rotates and revokes a prior session; logout
revokes server state; expiry is checked by the store. Development/test uses a
non-Secure cookie only for local HTTP. Production validation requires
`__Host-smhai_session`, Secure, HttpOnly, SameSite=Lax, Path=/, and no Domain.

## 10 CSRF

The synchronizer token is random and bound to the server-side session.
Cookie-authenticated mutations require `X-CSRF-Token` and also check allowed
Origin/Referer and `Sec-Fetch-Site`. Missing, invalid, cross-origin, and
cross-site mutation cases are rejected; safe reads do not require CSRF.

## 11 Authorization

`NativeAuthorizationProvider` is the Round 1 authority. It evaluates function,
object, and subject data scope for each resource operation. Review functions
require REVIEWER or ADMIN. OPA is not used for generic Backend authorization;
its future adapter remains possible through the port.

## 12 BOLA / BOPLA / BFLA

The security test matrix proves Student B cannot read Student A's report,
students cannot access review functions, and strict request DTOs reject
mass-assignment fields such as a foreign subject. Response DTOs are explicit
projections and do not return blocked candidate content.

## 13 Rate Limiting

Login and support use separate, configuration-driven in-memory buckets. The
test configuration demonstrates 429 with `Retry-After`. This is a
single-process engineering baseline, not distributed production rate limiting.

## 14 Problem Details

Application errors use RFC 9457-style Problem Details with
`application/problem+json`, stable error code, type, title, status, detail,
request_id, trace_id, and optional retry metadata. Stack traces, secrets,
paths, SQL, and raw upstream responses are not exposed. Errors use semantic
non-200 status codes.

## 15 Request/Trace Context

Middleware creates bounded `request_id` and `trace_id` values and accepts valid
correlation headers. Backend forwards request/trace context to the real Safety
HTTP adapter and trace IDs to the application integration ports. Optional
W3C `traceparent` is preserved without replacing the project correlation ID.

## 16 Logging

structlog is configured with JSON rendering and safe context fields. Ordinary
logs contain method, route, status, latency, request/trace IDs, and other safe
metadata only. Passwords, cookies, CSRF tokens, raw psychological messages,
prompts, candidates, and full Safety payloads are excluded. The vertical slice
captured-log assertion passed.

## 17 Audit

`AuditService` writes typed, safe metadata for login, logout, access denial,
assessment lifecycle, support requests, and review actions. Audit events are
separate from operational logs and contain no raw message, password, prompt,
candidate, or assessment answer.

## 18 Repository Ports

User, session, assessment, conversation, report, review projection, audit,
idempotency, and unit-of-work ports are defined independently of persistence.
No SQLAlchemy, Alembic, DDL, SQL, or production database adapter was created.

## 19 InMemory Adapters

The required in-memory repositories and session/idempotency stores are present
and wired through the container. They are process-local, non-durable, not
multi-worker safe, and intentionally limited to synthetic Round 1 evidence.

## 20 CAT Integration

Result: `CONTRACT_FAKE`. The inspected CAT module exposes Python lifecycle APIs,
not a formal HTTP service. `CatClient` and `ContractFakeCatClient` preserve the

## 21 RAG Integration

Result: `CONTRACT_FAKE`. The inspected RAG module exposes retrieval Python

## 22 LLM Runtime Integration

## 23 Safety Integration

`SafetyClient` maps Safety responses into Backend-owned decision views.
`HttpSafetyClient` uses the actual Safety paths discovered in 08 Safety:
health, input, retrieval, output, and review transition. Unit tests use the
explicit fake only for isolated Backend tests; the real integration harness
uses `REAL_HTTP`.

## 24 Real Safety Evidence

The real local Safety service at `127.0.0.1:8190` reported READY with OPA,
Presidio, NeMo, Qwen3Guard, and human-review capabilities. The harness
`scripts/run_real_safety_integration.py` performed a normal Backend request
through real Safety input/retrieval/output checks and received `PROCEED`; it
then performed a crisis request and received `CRISIS_ROUTE` with a review
reference. The Backend app does not manage the Safety process lifecycle.
The same harness authenticated as the synthetic reviewer and completed the
real Safety review transition sequence; the Backend review action returned
`approved`.

## 25 Support Orchestration

The normal order is input Safety -> RAG -> retrieval Safety -> LLM Runtime ->
output Safety -> buffered DTO. Any non-proceed decision stops the normal path.
The normal real-Safety run returned a generated result only after output
approval, and the fake vertical slice asserted the call order.

## 26 Crisis Route

The synthetic crisis fixture reaches Safety input and returns `CRISIS_ROUTE`,
an approved deterministic Safety response, a review reference, and
`normal_generation=false`. RAG call count and LLM call count remain unchanged
at zero for the crisis request. Crisis is a domain workflow result, not an
HTTP 500.

## 27 Output Safety

The synthetic unsafe candidate is sent to output Safety but is never returned
to the frontend. The test asserts `status=needs_review`, `content=null`, and
absence of the unsafe marker in the HTTP response. Raw token streaming is not
exposed.

## 28 Review Projection

Backend stores a frontend-readable review projection containing report,
assessment, generation, reason-code, Safety action, and status references.
Safety remains authoritative for Safety semantics; real review transitions are
called through the Safety adapter when a real case reference exists.

## 29 Idempotency

Assessment creation demonstrates same key plus same payload returns the
original response without a second CAT side effect. Reusing the key with a
different payload returns 409 Conflict. No generic retry is applied to
non-idempotent generation or workflow POSTs.

## 40 Data Privacy

No ordinary log or frontend DTO contains raw password, cookie, CSRF token,
assessment answer, psychological message, LLM prompt, LLM candidate, or full
Safety payload. Safe metadata uses lengths, digests, identifiers, statuses,
reason codes, and citation counts where needed. The output gate discards unsafe
candidate content before publication.

## 41 Real Student Data

NONE. All identities, assessment records, messages, citations, review cases,
and model candidates in tests and harnesses are synthetic fixtures.

## 42 Known Limitations

Persistence and relationships are process-local. Rate limiting and sessions are
not distributed. CAT, RAG, and LLM Runtime need formal versioned service
contracts. Production TLS/egress, school-specific authorization, persistent
review relationships, deployment process management, streaming Safety, and
clinical review remain outside this acceptance.

## 44 Deferred Items

Persistent Database adapters/schema, distributed sessions and rate limits,
OAuth/OIDC, MFA, password reset, production HTTPS, OpenTelemetry exporter/
collector, Prometheus, workers/queues, Kubernetes/service mesh, production
process supervision, and user-facing streaming remain deferred. These are not
silently represented as completed capabilities.

## 45 Round 2 Recommendation

First obtain and acceptance-test the CAT/RAG/LLM Runtime public contracts.
Then replace the in-memory ports behind the same domain services, add a
deployment-owned production session/rate-limit strategy, and define a
versioned streamed-Safety contract before considering any student-facing
streaming. Preserve the current fail-closed and no-real-data boundaries.
